# 工程能力路线与面试演示

目标是能从一个真实问题解释代码、取舍和失败边界，并能独立修改、验证和排错。项目功能的数量、框架名或测试条数不能保证录用。

## 当前可讲的能力

| 能力 | 具体证据 | 应同时说明的边界 |
|---|---|---|
| API 与身份 | JWT、资源归属、UUID 参数校验 | 知道资源 ID 不等于有权限 |
| 连续对话 | 成功历史、摘要、子 Agent 笔记及来源失效检查 | 摘要有损，不是无限长期记忆 |
| 检索工程 | BM25、Dense、RRF、索引发布版本和降级元信息 | 有限词法范围，fixture 不是实际 Embedding 质量 |
| 主/子 Agent 协作 | 工具循环、RAG 子 Agent、研究条件图 | 多 Agent 需实际任务理由，不是越多越好 |
| 任务可靠性 | PostgreSQL 队列、独立 worker、claim、lease 和写入栅栏 | 不支持整个执行图断点续跑，不保证恰好一次收费 |
| 请求幂等 | 相同意图复用、键冲突 409 | 解决入队，不是供应商幂等 |
| 成本与观测 | 原子共享预算、调用层级、usage、时延、请求编号 | Token 预留不是金额；usage 可以未知 |
| MCP 与 Skills | 官方 SDK stdio、固定只读工具、审核配方按需加载 | 单用户进程，不是通用远程 OAuth 平台或代码沙箱 |
| 验证 | 隔离数据库、供应商替身、协议测试、排序评估 | 真实质量、成本、容量需要另测 |

## 十分钟演示脚本

准备两份没有隐私的短文档，例如“方案 A 预算 30、方案 B 预算 90”，使用独立测试账号。若调用真实供应商，先设置小预算并记录模型和检索版本；离线演示要明确标注 fixture。

1. **一分钟介绍问题。** 展示 `/chat`：同一会话使用私有知识和网页研究，回答可以追溯到证据。
2. **两分钟展示知识与追问。** 选择知识库，询问方案 A，再追问方案 B。指出第二轮输入来自持久历史/笔记，不是浏览器保留的文字。点击来源核对数据。
3. **一分钟展示检索依据。** 查看型号/专有名词查询的词法候选、向量候选、RRF 排名和版本。解释同一个查询为什么可能有不同排序，不把融合分数当置信度。
4. **两分钟展示执行生命周期。** 用假供应商案例演示 queued 在 API 重启后保留、同键复用和 running 失联后不自动重跑；展示 lease 失效不能写迟到结果。
5. **一分钟展示调用记录。** 从 turn ID 打开 execution API，展示父子调用、调用次数、Token 预留与实际 usage；缺失 usage 保持未知。
6. **一分钟展示扩展边界。** 官方 MCP 客户端发现六个工具，读取一个有权知识库；展示 SKILL.md 元信息和显式加载，说明模型不能指定 user_id。
7. **两分钟展示评估与取舍。** 运行固定检索评估，比较 BM25、向量 fixture、RRF。挑一个失败案例说明原因及下一次实验，不念一个脱离数据集的总分。

演示时优先完成一条完整链路，工具进度、测试和配置用来解释结果，不让多个终端取代用户体验。真实演示结果与自动化替身结果分别标明。

## 常见追问的回答方向

- **为什么不用单 Agent？** 先给一个 RAG 或研究中间结果隔离上下文的具体例子，再说额外调用的时延和费用。没有这个收益的请求直接回答。
- **为什么 PostgreSQL 队列？** 业务事务和执行意图一起提交，当前规模下减少额外基础设施；代价是数据库轮询、维护和大规模吞吐边界。Redis 当前只用于可选公开缓存。
- **为什么不能自动重试所有失败？** 请求超时可能发生在供应商已经执行之后。先区分确定拒绝和结果未知，再决定如何处理；本版不自动重放失联执行。
- **为什么不是 exactly-once？** 本地事务/lease 可以控制入队与写库，跨供应商请求和进程崩溃仍存在不可原子提交窗口。
- **哪些工作进入队列？** 统一聊天、研究和文档索引三类；文件上传完成不代表索引 ready，ready 发布同样受 lease 约束。独立知识库旧问答仍有自己的路径，需要分别验证。
- **为什么混合检索？** 型号/术语和语义表达各有长处，用排名融合避免直接混加不可比的分数；用同一数据集和消融结果判断是否改善。
- **如何证明追问真的记住？** 检查第二轮实际发给模型的上下文与来源校验，不只看界面展示的上一条回答。
- **如何控制成本？** 共享预留和次数限制阻止后续派发，usage 记录实际已知消费；没有价格表和供应商账单核对，不能称金额硬上限。
- **技能文件被注入怎么办？** 固定审核名单、路径校验、不执行脚本，权限在服务端；说明正文是流程数据，不能授予新权限。

## 接下来需要亲手完成的实验

### 一、真实供应商与答案质量

用小而明确的测试集完成一次真实 DeepSeek/智谱/Tavily 联调，记录模型版本、提示词、检索参数、结果、时延和 usage。检查流式 usage、工具调用参数、拒答与超时。人工逐条核对主张和来源；不能用模型自己的“正确”评价代替标注。

用户自己应能改一个检索参数或提示词，预测影响，再比较结果。先做这一轮，才有依据写真实简历中的质量和成本数字。

### 二、领域评估集和失败归因

将真实且允许使用的领域问题标为开发集和留出集，写清相关文档/片段以及无答案问题。固定留出集后比较词法、Dense 和融合；按权限、过期资料、同义表达、型号、否定条件分类错误。再决定是否需要 reranker、查询改写或更换 Embedding，而不是先安装全部热门模块。

### 三、故障与资源边界

亲手运行幂等重发、停止 worker、过期 lease、取消、数据库短暂不可用和预算耗尽实验，写出观察到的状态。分别说明“未发出”“已发出但未知”“结果已返回但未保存”三个窗口。

### 四、有证据再扩展

- 需要长任务从中间继续时，设计持久 checkpoint、输入版本与节点幂等，测试恢复中的外部副作用，不能只加一张表。
- 需要写回/发布/执行工具时，再引入与同一授权任务绑定的审批和明确执行边界。
- 本地 trace 不足时评估 Langfuse/OTel 的脱敏、保留和部署方案；当前没有默认向外上传私有 prompt。
- 用同一评估集为 Deep Agents 做薄适配对照，只有质量、维护或可靠性收益清楚时再迁移。
- 有真实改代码执行任务时再评估 OpenHands/沙箱，当前知识研究应用不需要为了名称引入任意代码执行。

岗位所需 Java/Python、SQL、网络、事务、并发、Git 和 Linux 基础仍需单独练习。项目的价值在于能把基础知识解释到具体请求和故障中。
